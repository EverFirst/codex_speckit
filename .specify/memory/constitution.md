# TODO API Constitution

## Core Principles

### Architecture Discipline
- All functionality MUST be delivered through RESTful HTTP APIs that expose predictable resource-oriented URIs.
- Each endpoint MUST stay stateless; state is persisted only in the database, never in process or session memory.
- Each endpoint MUST have a single, clear responsibility and return consistent JSON envelopes.
- The product scope prioritizes core todo features without authentication/authorization until the roadmap explicitly green-lights them.
**Rationale**: A narrowly scoped, stateless REST interface keeps the service interoperable and easy to reason about as new clients are added.

### Technical Stack Standards
- Python 3.11+ with FastAPI (current stable release) is the only approved application stack.
- SQLite is the default database, with SQLAlchemy Core for all data access; no ORM abstractions are allowed.
- Swagger UI generated by FastAPI MUST remain enabled, and all request/response models MUST use Pydantic for validation.
**Rationale**: A constrained, modern stack reduces decision overhead and guarantees compatibility with existing tooling and hosting targets.

### Quality Guarantees
- Core business logic MUST be covered by automated tests achieving at least 70% line coverage via pytest-cov.
- API responses MUST meet p95 latency under 200 ms in staging benchmarks that mirror production settings.
- Every endpoint MUST provide explicit error payloads with actionable messages, and the global OpenAPI document MUST remain valid (3.0 spec).
- Database schema changes MUST be captured through Alembic migrations that run as part of deployment.
**Rationale**: Quantified performance and coverage targets ensure regressions are caught before release and contracts remain trustworthy.

### Development Workflow
- Test-driven development is mandatory: write the failing test, implement the feature, then verify green before refactoring.
- Follow REST verb semantics strictly (GET read, POST create, PUT/PATCH update, DELETE remove) with matching HTTP status codes (200/201/400/404/500).
- Enforce Black for formatting, isort for imports, and complete type hints in all application modules.
**Rationale**: Consistent workflow and style controls keep contributions predictable and reduce integration friction across contributors.

### Security & Performance Safeguards
- All SQL must use SQLAlchemy parameter binding to eliminate injection risks.
- Every request payload MUST be validated through Pydantic models before touching business logic.
- Configure CORS only when a concrete client requires it, and keep the policy as narrow as possible.
- Rate limiting is deferred until a future release, but each new endpoint MUST document how it would behave under throttling.
**Rationale**: Enforcing validation and safe data-access primitives preserves trust and buys time until advanced controls (like rate limiting) are prioritized.

## Documentation & Knowledge Stewardship
- Keep README current with project description, local setup, run/test instructions, and an endpoint summary.
- Maintain self-documenting APIs via FastAPI's autogenerated Swagger UI; do not disable docs in non-production environments.
- Provide concise comments only where logic is non-obvious; prefer clear code and shared specs over inline explanations.
- Store per-feature specifications under `specs/` to keep requirements, decisions, and contracts auditable.
**Rationale**: Centralized, continuously updated documentation lowers onboarding cost and keeps API consumers aligned with implementation reality.

## Testing, Deployment & Evolution

### Testing Strategy
- Use pytest for all unit and integration suites, backed by FastAPI's TestClient for request/response verification.
- Run integration tests against an in-memory SQLite database configured to mirror production schema and constraints.
- Track coverage with pytest-cov and fail builds that dip below 70% on critical modules.
**Rationale**: A unified testing toolchain plus consistent data stores ensures test fidelity without external dependencies.

### Deployment & Operations
- Required environment variables include `DATABASE_URL` and any feature flags or secrets referenced in code; document defaults in `.env.example`.
- Application startup MUST run idempotent table creation/migration to guarantee schema availability before serving traffic.
- Provide structured logging with INFO-level request traces and ERROR-level stack traces; logs MUST be human- and machine-readable.
- Expose `GET /health` returning service readiness so automation and operators can gate rollouts.
**Rationale**: Explicit operational contracts keep deployments repeatable and observable across environments.

### Evolution & Change Management
- Develop feature-by-feature with isolated specs, tests, and deployable slices to preserve independence.
- Breaking API changes require semantic version bumps (v1, v2, ...) and parallel support for existing consumers until deprecation completes.
- Default to backward compatibility; additive changes are preferred and MUST be communicated through release notes.
- Follow feature branch naming `###-feature-name` and Conventional Commits to keep history searchable.
**Rationale**: Predictable branching and version management reduce risk while enabling rapid iteration when the roadmap expands.

## Governance
- This constitution supersedes other development guidance; all reviews MUST verify conformance before approving changes.
- Amendments require maintainer consensus, documented rationale, and version increments per semantic rules (major for breaking shifts, minor for new principles, patch for clarifications).
- Compliance reviews should occur at the start and end of each feature cycle to confirm plans, specs, and tasks incorporate the latest principles.
- Runtime guidance documents (plans, specs, tasks) MUST remain synchronized with this constitution whenever practices change.
